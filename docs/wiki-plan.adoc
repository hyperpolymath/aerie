= Aerie — Wiki Development Plan
:toc: preamble

Structured per the `metadatastician/berrywiki` pattern: three audiences,
**maximum 3-ply depth** (no page nested deeper than three levels), and
**maximum span of 7** at any layer (no home/index page links to more than
seven children). Content is plain GitHub-compatible Markdown (the berrywiki
ruling: wikis are the `.md` home; everything outside wikis stays `.adoc`).

== Audience framework

. **Users** — run, read, and trust the diagnostics.
. **Platform maintainers** — operate the stack and the estate wiring.
. **Developers** — extend the gateway, ABI, and specs.

== Page map (≤3 ply, ≤7 span)

=== Level 0 — Home (span 3, one per audience)

| Page | Audience | Content

| `Users`
| users
| First-run in five minutes; what each number on the HUD means; trust model (zero telemetry, proof envelopes); troubleshooting.

| `Platform maintainers`
| maintainers
| Stack operations: compose/Podman, Cloudflare/WAF, retention, upgrades, the estate wiring (CI, submodules, mirrors).

| `Developers`
| developers
| Architecture law, build system, spec pipeline, how to add a module end-to-end.

=== Level 1 — Users (span 5)

| Page | Content
|------|-------

=== Level 1 — Developers (span 7)

| Page | Content
|------|-------
| `Architecture law`
| ABI = Idris2, FFI = Zig, API = Zig; the tracked-drift boundary (src/api/rust).
| `Build & test`
| build.zig, the Justfile verb matrix, `zig build test`, the Idris2 model suite, Guix/mise toolchains.
| `Spec pipeline`
| K9/SVC components, guarded outputs, `just specs*`, the manifest guard.
| `Adding a module`
| End-to-end: spec → Zig client → resolver → GraphQL field → HUD widget → tests → docs.
| `ABI & proofs`
| src/abi layout, proof envelopes, the LEAN4 targets (ROADMAP P1–P3).
| `CI & gates`
| The workflow set, traffic-light categories, dogfood gate, validation.
| `Code style & estate policy`
| Language policy, licence split, Oxford British English, commit rules.

== Development order (scaffolding first)

1. Home + the three audience pages (span 3) — the skeleton.
2. Users pages (highest leverage; README already half-does this job).
3. Developers: Build & test + Architecture law (agent-readability).
4. Platform maintainers: Deploying + Hardening.
5. Backfill the remaining pages as the features they describe land
   (a page whose feature is ROADMAP carries a `status: planned` callout).

== Invariants (enforced by review, berrywiki-style)

* No page deeper than 3 levels.
* No index page with more than 7 outbound page links.
* Every page carries an `Audience:` and `Status:` header line.
* Claims that assert behaviour must cite the code path or a spec output
  (the EXPLAINME discipline, applied to the wiki).
